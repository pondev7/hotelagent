## The concepts

### 1. Relational modelling: the three key kinds

- A **primary key** uniquely identifies a row. Ours are UUIDv7 (see S02).
- A **foreign key** points at another table's primary key, and the database
  *enforces* that the target exists. `booking.hotel_id` cannot reference a hotel
  that was never created.
- A **unique constraint** says a value may appear at most once. It is not
  decoration — it is the enforcement mechanism behind the whole of §6 below.

**One-to-many** is the shape almost everything here takes: one hotel has many
room types, so the *many* side carries the key. `room_type.hotel_id` exists;
there is no list of room types stored on the hotel. This trips people up
coming from object models, where a `Hotel` object naturally holds a list.

### 2. `ON DELETE`: the most consequential four characters in the schema

Every foreign key must answer: what happens if the target row is deleted? We use
all three answers deliberately, and the choice encodes a business rule.

```python
ForeignKey("city.id", ondelete="RESTRICT")  # refuse the delete
ForeignKey("hotel.id", ondelete="CASCADE")  # delete the children too
ForeignKey("room_type.id", ondelete="SET NULL")  # keep the row, forget the link
```

- **`RESTRICT`** on `booking.hotel_id` and `conversation.user_id`. You cannot
  delete a hotel that has bookings, or a traveller who has a conversation. The
  database refuses. This is deliberate: financial and conversational history
  must not evaporate because someone tidied up a directory.
- **`CASCADE`** on `room_type.hotel_id` and `message.conversation_id`. A room
  type has no meaning without its hotel; a message has none without its thread.
  Deleting the parent should take them with it.
- **`SET NULL`** on `call_task.room_type_id`. If a hotel restructures its room
  types, the historical call task should survive with a null pointer rather than
  vanish — the *fact that we phoned* is data we want to keep (invariant #8).

Getting this wrong is how you either can't delete anything, or delete far more
than you meant to.

### 3. Indexes, and why column order matters

An **index** is a sorted structure letting the database find rows without
scanning the table. Without one, "find open call tasks in Kanyakumari" reads
every row.

Indexes are not free: each one is extra work on every insert, update and delete,
plus disk. So you index what you actually query.

**Composite index column order is the part worth understanding.**

```python
Index("ix_call_task_city_id_status_opened_at", "city_id", "status", "opened_at")
```

A composite index works like a phone book sorted by surname, then first name.
It can answer "everyone called Patel", and "Patels called Anu" — but it is
useless for "everyone called Anu", because the first column is what the
structure is sorted by.

So the rule is **leftmost prefix**: an index on `(a, b, c)` serves queries
filtering on `a`, on `(a, b)`, or on `(a, b, c)` — never on `b` alone. Ours
leads with `city_id` because every tenant-scoped query filters by city first
(invariant #1), then narrows.

This is also why S02's redundant index was dropped: an index on `(city_id,
integration_tier)` already serves `city_id` alone, so a separate `city_id` index
was pure write cost.

### 4. `CHECK` constraints: rules the database enforces

```python
CheckConstraint("check_out > check_in", name="stay_is_at_least_one_night")
CheckConstraint("commission_amount >= 0 AND commission_amount <= amount", ...)
```

Application code can be bypassed — a migration, a fix-up script, a psql session
at 2am during an incident. A `CHECK` constraint cannot. For anything where a
violation would be *corrupt data* rather than merely *a bug*, put it in the
database.

Our constraints encode real invariants: a stay is at least one night, guests is
positive, commission never exceeds the amount it is taken from. Note that last
one — it makes an entire class of billing bug unrepresentable.

### 5. Nullability is a design decision

`Mapped[str]` is `NOT NULL`; `Mapped[str | None]` is nullable. Each column is a
small assertion about the world:

- `booking.amount` is `NOT NULL` — a booking without an amount is meaningless.
- `hotel.reception_phone` is nullable — a Tier A hotel may never need one.
- `message.external_id` is nullable — an outbound message has no provider id
  until the provider accepts it.

The default instinct should be `NOT NULL`. Every nullable column is a branch
every future reader of that column must handle, forever.

### 6. Native enums, `StrEnum`, and the reserved-word trap

Our enums are Python `StrEnum` mapped to native PostgreSQL enum types, so the
database rejects a value outside the set. Three practical notes:

**`StrEnum`** (Python 3.11+) members *are* strings, so `IntegrationTier.MANUAL
== "manual"` is true and JSON serialisation works with no special casing.

**Adding a value is easy; removing one is not.** `ALTER TYPE ... ADD VALUE`
exists. There is no `DROP VALUE` — removing one means creating a new type,
migrating every column, and dropping the old. Design enums additively.

**`app_user`, not `user`.** `user` is a reserved word in PostgreSQL —
`SELECT * FROM user` returns the current username rather than your table. You
can quote your way around it forever, or rename once. We renamed.

### 7. JSONB: the escape hatch, used sparingly

`JSONB` stores structured JSON with indexing and querying support. We use it for
`city.config`, `hotel.policies`, `conversation.slots`, `message.attachments` and
`booking_event.payload`.

The discipline: **JSONB is for data whose shape we do not yet know, or that
genuinely varies.** Anything queried, constrained, or reported on gets a real
column. `commission_rate` is a column precisely because we filter and sum on it;
`policies` is JSONB because every hotel's policies differ and nothing joins on
them yet.

The failure mode is using JSONB to avoid writing migrations. You lose type
safety, constraints and cheap indexing, and gain a schema that only exists in
whatever code last wrote to it.

### 8. Event log vs event sourcing

`Booking` has a mutable `status`. `BookingEvent` records every state change,
append-only. Both exist on purpose, and the distinction between two ideas
matters here:

- **Event sourcing** (which we are *not* doing): events are the only truth, and
  current state is *derived* by replaying them. Powerful, and a large
  commitment.
- **An event log** (what we are doing): current state lives in ordinary mutable
  rows, *and* every change is also appended to a log.

We get audit, dispute resolution, analytics and replay for the cost of one extra
insert per state change, while ordinary queries stay ordinary.

**Why a `status` column alone is not enough.** It answers "where is this booking
now?" and destroys the answer to everything else. When a hotelier disputes a
commission, or a traveller says they cancelled in time, `status = "cancelled"`
tells you nothing about *when*, *who* or *why*. That history cannot be
reconstructed later, which is why invariant #6 says "from day one".

Note `BookingEvent` has no `updated_at`. An event happened once, at
`occurred_at`. An "updated" timestamp on an immutable record is a contradiction.

### 9. Enforcing append-only with SQLAlchemy events

A comment saying "do not UPDATE this table" is a wish. This makes it a rule:

```python
@event.listens_for(Session, "before_flush")
def _forbid_mutation(session, flush_context, instances):
    for obj in session.dirty:
        if isinstance(obj, AppendOnlyMixin) and session.is_modified(obj):
            raise AppendOnlyError(...)
```

**SQLAlchemy's event system** lets you hook lifecycle moments. `before_flush`
fires just before the session translates its tracked changes into SQL — the last
moment where you can see intent and refuse.

The session tracks objects in collections: `session.new` (to be inserted),
`session.dirty` (loaded and possibly modified), `session.deleted`. Note the
`session.is_modified(obj)` check — `dirty` is *optimistic*, listing objects that
might have changed, so touching an attribute without changing its value lands
there too.

**This is defence in depth, not a guarantee.** It stops application code. A raw
`UPDATE` in psql sails past it, because the ORM is not involved. Real
enforcement is a database rule or trigger, and belongs with M5's hardening.
Layered defences that each catch a different class of mistake are the norm; a
single perfect one is usually a fantasy.

### 10. Idempotency: the actual mechanism

**Idempotent** means: doing it twice has the same effect as doing it once.

Four things guarantee you will need this:

- WhatsApp redelivers a webhook if your 200 was slow.
- Payment gateways retry callbacks they think failed.
- Operators double-click.
- Clients retry requests that actually succeeded.

The naive fix — "check whether it exists, then insert" — is broken under
concurrency. Two requests can both check, both find nothing, and both insert.
The window between check and write is small, and small windows are hit
constantly at any real volume.

**The correct mechanism is to let the database arbitrate:**

```python
pg_insert(IdempotencyKey)
    .values(scope=scope, key=key)
    .on_conflict_do_nothing(index_elements=["scope", "key"])
    .returning(IdempotencyKey.id)
```

`INSERT ... ON CONFLICT DO NOTHING` is PostgreSQL's atomic "insert unless it
exists". If a row comes back, you won the race and should do the work. If
nothing comes back, someone else already claimed it and this is a replay.

Two simultaneous callers cannot both win: the unique index serialises them. The
second blocks until the first commits, then sees the conflict. **No
application-level check can promise that** — the guarantee comes from the index.

**Scope** namespaces the key, so a WhatsApp message id and a payment gateway
event id cannot collide even if the strings match.

**Transaction placement matters.** The claim and the work share one transaction
deliberately, so a failed operation rolls the claim back with it. Otherwise a
transient gateway timeout would leave a claimed key behind and permanently block
a legitimate retry — turning a blip into a lost booking.
`test_a_failed_operation_does_not_poison_the_key` pins that behaviour.

### 11. NULLs in a unique constraint

```python
UniqueConstraint("external_id", name="uq_message_external_id")
```

`message.external_id` is nullable *and* unique. In PostgreSQL these coexist,
because **NULL is not equal to itself** — so any number of rows may have a NULL
here, while two rows with the same non-NULL id are rejected.

This is exactly what we want: outbound messages without a provider id yet coexist
happily, while a redelivered inbound message is refused by the index. It also
surprises people who expect `UNIQUE` to permit only one NULL, which is how some
other databases behave.

### 12. Double-entry bookkeeping, briefly

`LedgerEntry` follows accounting practice that predates computers by centuries,
for good reasons.

- **Amounts are always positive.** Direction is a separate `debit`/`credit`
  column. Signed amounts plus a direction column is how you end up
  double-negating a refund and reporting income you never received.
- **Accounts** are the buckets money moves between: `CUSTOMER_RECEIPTS`,
  `HOTEL_PAYABLE`, `COMMISSION_INCOME`. A single booking touches several — we
  collect from the traveller and settle net to the hotel, so the customer's
  ₹2,600 becomes ₹390 commission income and ₹2,210 payable.
- **Corrections are reversing entries, never edits.** This is why `LedgerEntry`
  is append-only. A mistake stays visible and is cancelled by an opposite entry.
  An audit trail you can edit is not an audit trail.

At M1 the entries are typed in by hand from UPI references. The shape is
identical to what the gateway will write at M4, which is the entire reason for
building it now.

### 13. Copying `commission_rate` onto the booking

```python
commission_rate: Mapped[Decimal] = mapped_column(Numeric(5, 2), nullable=False)
```

The hotel already has a `commission_rate`, so why store it again?

Because a booking must record the terms **as they were when it was taken**. When
a hotel digitises and moves from Tier C's 15% to Tier B's 13%, that must not
retroactively rewrite the economics of every booking already settled. Joining to
the hotel for the rate would do exactly that.

This is the difference between a *reference* and a *snapshot*, and money almost
always wants a snapshot. The same reasoning will apply to prices at M4.

## Reading our code

### Why `enums.py` exists

The module boundary rule forbids one module importing another's **models**.
`IntegrationTier` is needed by `inventory` (a property of a hotel) and by
`availability` (the source of an observation).

Duplicating it would be worse than sharing it: two definitions of `"manual"` that
can drift apart is exactly the bug that surfaces as a mismatched string in
production months later. So genuinely shared vocabulary lives in
`hotelagent/enums.py`, which is not a module and belongs to nobody. Enums used by
one module only — `BookingStatus`, `CallTaskStatus` — stay where they are used.

The rule is about **ownership of data**, not about never sharing a name.

### The three bugs autogenerate produced

S02's notes claimed autogenerate mishandles enum types. This slice proved it
concretely, and two of the three break the *upgrade*, not merely the downgrade:

1. **Zero enum drops in `downgrade()`.** All thirteen new types would have been
   orphaned, and the next upgrade would fail with "type already exists".
2. **`channel` emitted twice** — once for `app_user`, once for `conversation`.
   Each `create_table` independently emits `CREATE TYPE`, so the second fails.
3. **`integration_tier` re-created**, though migration 0001 already owns it.

The fix is one pattern: declare each type once at module level with
`create_type=False`, create them explicitly at the start of `upgrade`, drop them
in reverse at the end of `downgrade`, and leave types owned by an earlier
migration alone.

**The lesson generalises past enums.** Autogenerate is a drafting tool. Read
every migration it writes, especially the `downgrade`, which nothing exercises
until the day you urgently need it.

### The two verifications worth stealing

**The drift check.** After applying the migration, run autogenerate again. If it
produces an empty migration, your models and your migration agree. If it
produces anything, they have diverged — usually because a hand-edit drifted from
the model.

**The re-upgrade test.**

```python
command.upgrade(alembic_config, "head")
command.downgrade(alembic_config, "base")
command.upgrade(alembic_config, "head")
```

Three lines that catch the entire class of "downgrade left something behind".
A downgrade tested only by running it looks fine; only re-upgrading proves it.

## The gotchas

**`user` is reserved in PostgreSQL.** Use `app_user`.

**Composite indexes only serve a leftmost prefix.** An index on `(a, b)` does
nothing for a query filtering on `b` alone.

**Redundant indexes cost writes.** `(city_id, status)` already covers `city_id`.

**Enum values are easy to add and hard to remove.** Design additively.

**`session.dirty` is optimistic** — it lists objects that *might* have changed.
Pair it with `session.is_modified()`.

**Check-then-insert is not idempotent.** Only a unique constraint plus
`ON CONFLICT` is safe under concurrency.

**Claiming an idempotency key outside the operation's transaction** turns a
transient failure into a permanently blocked retry.

**NULL is not equal to itself**, so a unique column may hold many NULLs.

**Autogenerate mishandles enum types, renames and `CHECK` constraints.** Read
what it writes.

**An async fixture cannot call Alembic.** `env.py` runs `asyncio.run()`
internally, and nesting event loops raises. Keep migration fixtures synchronous
— this bit us directly in this slice.
